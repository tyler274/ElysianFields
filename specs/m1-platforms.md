# M1 Target Platforms and Qualification Tiers

This specification is Gatekeeper (Aponia)-approved for Builder (Vill-V) consumption inside the Elysian Realm. It enumerates every target platform in scope for Elysian Fields, its canonical requirement-ledger platform key, required OS/browser versions, graphics backend requirements, deployment channel, and representative low/midrange hardware qualification tier.

## 2. Platform Architecture and Qualification Rules

- **Subpath deployment**: All browser Wasm bundles, assets, and API routes must work cleanly under the `/elysianfields/` subpath rather than assuming domain root `/`.
- **Platform adapter boundary**: Dedicated platform adapter modules own HTTP and event streams, secure credential storage, file pickers/providers, deep links, push notifications, IME and clipboard integration, OS health APIs (HealthKit / Health Connect), and suspend/resume/process-recreation lifecycles.
- **Single accessibility and input owner**: Any narrow text-input or accessibility bridge must keep one authoritative state owner without duplicating editable content or screen-reader nodes.
- **Extension split**: Browser extension background service workers and EHR content scripts remain ordinary extension scripts; only the popup UI is evaluated for canvas rendering under strict MV3 CSP and cold-start/size budgets (`specs/m1-feasibility-budgets.md`).
- **Desktop requirement (Decision D4)**: Linux, macOS, and Windows desktop builds are all required targets and must produce real-hardware M1 qualification evidence (text/IME, screen readers, graphics backend, and build/link time) before M2.
- **Honest coverage reporting**: Any platform lacking physical test hardware during a qualification run is recorded as `blocked` (`blocked-no-hardware`), never `passed` and never silently waived.
